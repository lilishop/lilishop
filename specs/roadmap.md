# Lilishop 产品路线图

> 整体先后顺序以四仓 `README.md` 为准：先稳住已交付基线，再按「升级计划」中 🔜 条目的书写顺序推进。  
> 阶段 0 插在功能开发之前，专门消化 README「架构文档边界」与访谈确认的全部短板。  
> 目标用户见 [mission.md](./mission.md)：平台运营方、入驻商家、C 端消费者、二次开发团队。  
> 访谈确认：微信小店 / 抖店对接不进入本次 specs 与路线图。

## 0. 阅读约定

- 每个迭代只做一件可验收的小事，默认可在 1～2 个工作日内完成。
- 跨仓改动必须在迭代标题中标明仓库：`lilishop` / `lilishop-ui` / `lilishop-uniapp` / `docker`。
- 状态：`已完成` 来自 README「✅」；`待做` 来自 README「🔜」或访谈短板。
- 不在本路线图中重新实现已打 ✅ 的能力，只把它们当作基线约束。
- 不把渠道对接、Spring Cloud 引入、Elasticsearch 恢复写成迭代。

## 1. 基线（README 已完成，禁止回退）

以下能力视为当前可商用 B2B2C 的最低集合，后续迭代不得破坏：

| 序号 | 能力 | 主要用户 |
| --- | --- | --- |
| B1 | 商品定时上下架 | 商家、平台 |
| B2 | 商品分组 | 商家、平台 |
| B3 | 会员分组 | 平台 |
| B4 | 商品虚拟销量 | 商家 |
| B5 | 专用发票（发票上传） | 商家、消费者 |
| B6 | 置顶评论 | 商家、平台 |
| B7 | 客户等级 | 平台、消费者 |
| B8 | 购物卡 | 平台、消费者 |
| B9 | 腾讯云-云直播 | 商家、消费者 |
| B10 | 统计：营业 / 商品 / 会员 / 积分 / 储值 / 营销 / 分销 | 平台、商家 |
| B11 | 经营报表（店铺业绩、商品同比环比、销售订单明细、商品销售汇总） | 平台、商家 |
| B12 | 卡密商品 | 商家、消费者 |
| B13 | 二级分销 | 平台、商家、消费者 |

## 2. 阶段 0 — 规范对齐与四仓契约（短板优先）

### 迭代 0.2 — 对齐 `lilishop` README 徽章与正文

- 仓库：`lilishop` + `docker`

### 迭代 0.7 — 统一产品版本号

- 仓库：`lilishop`
- 产出：`config/application.yml` swagger `4.2.2`、`im-api` `1.0.0` 与父 POM `4.3` 对齐为同一 revision
- 验收：OpenAPI 页、POM、发布说明使用同一个版本号

### 迭代 0.8 — 四仓职责一页纸

- 仓库：`lilishop`（`specs/`）
- 产出：四仓职责、演示地址、文档入口的单一索引（可附在 tech-stack 或独立 `repos.md`）
- 验收：二次开发团队能在 5 分钟内知道改后端 / 改 Vue / 改 Uniapp / 改 SQL 该去哪个仓

### 迭代 0.9 — 跨仓 API 契约规范

### 迭代 0.10 — 作废 `common-api` 旧路径

- 仓库：`lilishop` + `lilishop-ui` + `lilishop-uniapp`

### 迭代 0.11 — 跨仓环境变量与域名规范

### 迭代 0.12 — 写清 MariaDB 与 MySQL 口径

### 迭代 0.13 — 写清 lite / 完整打包 / 生产 三条边界

## 3. 阶段 1 — 主题色管理（README 🔜 第 1 项）

服务平台运营方配置品牌色，并下发到商家端、PC、Uniapp。必须跨仓。

### 迭代 1.1 — 主题色领域模型

- 仓库：`lilishop`
- 产出：平台级主题色字段（主色、辅色、危险色、背景、文字）与默认值
- 验收：库表 / 配置项可读写，不影响现有页面

### 迭代 1.2 — 平台端读取 / 保存 API

- 仓库：`lilishop`（`manager-api`）
- 产出：运营端获取、更新主题色的接口；非法色值拒绝
- 验收：仅平台角色可写

### 迭代 1.3 — 买家端公开读取 API

- 仓库：`lilishop`（`buyer-api`）
- 产出：无需登录即可读取当前生效主题色
- 验收：C 端启动时能拉到与平台配置一致的 token

### 迭代 1.4 — 商家端只读 API

- 仓库：`lilishop`（`manager-api` 商家域）
- 产出：商家端读取平台主题色（本阶段不做店铺自定义，除非后续单独立项）
- 验收：商家端与运营端看到同一套生效值

### 迭代 1.5 — 运营端设置页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：主题色表单、预览条、保存
- 验收：平台运营方可在管理端改色并持久化

### 迭代 1.6 — 商家端应用主题（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：商家端 CSS 变量接入平台主题
- 验收：改主色后商家端按钮 / 链接变色

### 迭代 1.7 — PC 商城应用主题（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：PC 商城 CSS 变量接入
- 验收：改主色后 PC 首页主按钮变色

### 迭代 1.8 — Uniapp 应用主题（`lilishop-uniapp`）

- 仓库：`lilishop-uniapp`
- 产出：H5 / 小程序 / APP 读取并应用主题变量
- 验收：同一配置在移动端可见

### 迭代 1.9 — 缓存与发布

- 仓库：`lilishop`
- 产出：主题色变更后失效 Redis 缓存；买家端短缓存
- 验收：保存后各端在约定 TTL 内看到新色，无需发版

### 迭代 1.10 — 阶段 1 回归

- 仓库：四仓
- 产出：基线页面（登录、下单、店铺装修）未因 CSS 变量回归；多语言文案不被色值硬编码破坏
- 验收：平台改色 → 四端一致；回默认值可恢复

## 4. 阶段 2 — 店铺结算汇总（README 🔜 第 2 项）

服务平台运营方与入驻商家。建立在已有经营报表（B11）之上，不重复做订单明细。

### 迭代 2.1 — 结算汇总口径确认

- 仓库：`lilishop`（`specs/` 可补一页口径）
- 产出：时间维度（日 / 周 / 月）、金额字段（应收、退款、佣金、运费、实结）定义
- 验收：平台与商家使用同一套字段名

### 迭代 2.2 — 汇总查询模型

- 仓库：`lilishop`
- 产出：按店铺 + 账期聚合的查询对象，不落新业务状态机
- 验收：对已有订单流数据可算出一条店铺汇总

### 迭代 2.3 — 平台端店铺结算汇总 API

- 仓库：`lilishop`（`manager-api`）
- 产出：筛选店铺、账期、分页、合计行
- 验收：平台可看到全部店铺汇总

### 迭代 2.4 — 商家端本店结算汇总 API

- 仓库：`lilishop`（`manager-api` 商家域）
- 产出：仅返回当前店铺；越权访问他店拒绝
- 验收：商家只能看自己的汇总

### 迭代 2.5 — 导出

- 仓库：`lilishop`
- 产出：平台 / 商家各自权限下的表格导出
- 验收：导出列与列表一致

### 迭代 2.6 — 运营端列表页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：筛选、合计、下钻到已有经营报表的入口
- 验收：平台运营方可按账期看各店汇总

### 迭代 2.7 — 商家端列表页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：本店结算汇总页
- 验收：与平台侧同一店铺、同一账期数字一致

### 迭代 2.8 — 阶段 2 对账抽检

- 仓库：`lilishop`
- 产出：抽 1 个店铺 1 个账期，汇总 = 已有订单 / 退款明细之和
- 验收：差额为 0 或可解释（四舍五入规则写明）

## 5. 阶段 3 — 支付方式汇总（README 🔜 第 3 项）

服务平台运营方。按支付渠道切分已有成交，不改支付渠道路由。

### 迭代 3.1 — 支付方式枚举对齐

- 仓库：`lilishop`
- 产出：微信 / 支付宝 / 钱包 / 线下等与现有支付插件一致的汇总维度
- 验收：未知支付方式进入「其他」，不丢单

### 迭代 3.2 — 汇总查询

- 仓库：`lilishop`
- 产出：按账期 + 支付方式聚合金额、笔数、退款
- 验收：全渠道之和等于阶段 2 可对上的平台总成交（口径书面化）

### 迭代 3.3 — 平台 API

- 仓库：`lilishop`（`manager-api`）
- 产出：列表 + 合计；可选按店铺过滤
- 验收：仅平台角色

### 迭代 3.4 — 导出

- 仓库：`lilishop`
- 产出：支付方式汇总导出
- 验收：与列表列一致

### 迭代 3.5 — 运营端页面（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：支付方式汇总表
- 验收：筛选账期后数字稳定刷新

### 迭代 3.6 — 阶段 3 对账抽检

- 仓库：`lilishop`
- 产出：抽一个账期，各支付方式金额之和 = 平台收款合计
- 验收：差额可解释

## 6. 阶段 4 — 结算台账（README 🔜 第 4 项）

服务平台与商家。在「汇总」之上提供可翻页的台账流水，为后续打款做底稿。

### 迭代 4.1 — 台账条目模型

- 仓库：`lilishop`
- 产出：一条台账 = 店铺 + 账期 + 业务单号 + 方向（应收 / 应退 / 调账）+ 金额 + 状态
- 验收：能从已有订单 / 售后生成样例条目

### 迭代 4.2 — 生成规则（只入账，不打款）

- 仓库：`lilishop`
- 产出：订单完成、售后退款写入台账的规则；幂等键
- 验收：同一业务单重复跑不产生第二条

### 迭代 4.3 — 平台台账查询 API

- 仓库：`lilishop`（`manager-api`）
- 产出：按店铺、账期、状态、单号筛选
- 验收：平台可跨店查询

### 迭代 4.4 — 商家台账查询 API

- 仓库：`lilishop`（`manager-api` 商家域）
- 产出：仅本店
- 验收：越权拒绝

### 迭代 4.5 — 台账与汇总勾稽

- 仓库：`lilishop`
- 产出：某店某账期台账净额 = 阶段 2 汇总对应字段
- 验收：自动对账任务或校验接口返回一致

### 迭代 4.6 — 运营端台账页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：台账列表、状态、跳转原单
- 验收：从汇总可下钻到台账

### 迭代 4.7 — 商家端台账页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：本店台账
- 验收：与平台同店同账期条数、金额一致

### 迭代 4.8 — 阶段 4 回归

- 仓库：`lilishop`
- 产出：退款单、取消单各抽一笔，台账方向正确
- 验收：不破坏 B11 经营报表

## 7. 阶段 5 — 钱包流水（README 🔜 第 5 项）

服务平台、商家（若有店铺钱包）、消费者。本仓已有钱包模块与流水表，本阶段补的是「可汇总、可对账、可给用户看清」的流水，而不是从零做钱包。

### 迭代 5.1 — 现有流水字段盘点

- 仓库：`lilishop`
- 产出：钱包模块已有日志类型、正负向、关联单号清单
- 验收：列出缺口（缺类型 / 缺关联 / 缺店铺维度）

### 迭代 5.2 — 补齐流水类型与关联

- 仓库：`lilishop`
- 产出：充值、消费、退款、佣金、提现、调账等类型齐全；每条能回到业务单
- 验收：新产生的钱包变动必有流水

### 迭代 5.3 — 消费者流水 API

- 仓库：`lilishop`（`buyer-api`）
- 产出：当前会员分页流水
- 验收：只能看自己

### 迭代 5.4 — 平台流水查询 API

- 仓库：`lilishop`（`manager-api`）
- 产出：按会员、类型、时间筛选
- 验收：脱敏级别遵守现有敏感字段策略

### 迭代 5.5 — 与结算台账的边界

- 仓库：`lilishop`
- 产出：书面区分「结算台账（店铺应收）」与「钱包流水（账户余额）」；禁止混用一张表冒充两套账
- 验收：财务同学能只看文档分清两套账

### 迭代 5.6 — PC / Uniapp 流水页

- 仓库：`lilishop-ui` + `lilishop-uniapp`
- 产出：消费者可查看钱包流水
- 验收：两端字段一致

### 迭代 5.7 — 运营端流水页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：平台查询会员流水
- 验收：与 API 筛选一致

### 迭代 5.8 — 阶段 5 对账抽检

- 仓库：`lilishop`
- 产出：抽 1 个会员，流水净额 = 钱包余额变动
- 验收：差额为 0

## 8. 阶段 6 — 财务汇总（README 🔜 第 6 项）

服务平台运营方。把阶段 2～5 收口成一张财务总览，不新开支付渠道。

### 迭代 6.1 — 财务总览口径

- 仓库：`lilishop`
- 产出：平台收入、店铺应结、退款、钱包沉淀、待结算，一张字段表
- 验收：每个字段能追溯到阶段 2～5 的某一个数

### 迭代 6.2 — 总览 API

- 仓库：`lilishop`（`manager-api`）
- 产出：按账期返回总览卡片 + 下钻链接标识
- 验收：仅平台角色

### 迭代 6.3 — 运营端总览页（`lilishop-ui`）

- 仓库：`lilishop-ui`
- 产出：财务汇总首页，卡片跳到结算汇总 / 支付方式 / 台账 / 钱包流水
- 验收：四个下钻入口可走通

### 迭代 6.4 — 总览导出

- 仓库：`lilishop`
- 产出：账期财务汇总导出
- 验收：与卡片数字一致

### 迭代 6.5 — 阶段 6 勾稽

- 仓库：`lilishop`
- 产出：总览四块数字与阶段 2～5 接口对账脚本或手工清单
- 验收：同一账期四处勾稽通过

财务相关阶段 2～6 必须按序：没有店铺结算汇总，支付方式汇总无法勾稽；没有台账，汇总不可审计；没有钱包流水口径，财务总览会把余额与应结算混在一起。

README 升级计划中的「微信小店对接」「抖店对接」按访谈结论不进入本路线图。Spring Cloud 引入、Elasticsearch 恢复均不进入本路线图；若未来要做，必须单独立项。
